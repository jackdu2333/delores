## 2. 新变化评审

### 2.1 Snap 触发回顶部中央（`27ae931a`）：宪法先行的正面范例 ✅

宠物侧 snap island 被整体移除（净删 ~300 行），snap 回到「当前显示器顶部中央」唯一入口，**同一次提交在宪法（delores-product.md）写入三行规则**："The Companion's position never acts as a split trigger"，架构文档同步改写仲裁描述。这是「定位层变化 → 宪法先行 → 代码跟上」的正确顺序，与上次评审发现的「pet-anchored snap 做完才回滚」形成对照——**这条工作流值得作为仓库的标准模式**。

### 2.2 Codex 宠物锚定（4 提交，约 900 行）：行为完整、定位未过堂 ⚠️

现状：`CompanionMode` 三态（`.off/.delores/.codex`）；`CodexPetWindowProbe`（377 行）读 Codex loopback DevTools（127.0.0.1:9341）的 mascot DOM 矩形 + activity pill，再经 WindowServer 确认 overlay 在屏；Codex 模式下划词工具栏从 Codex 宠物旁生长、跟随其显示器、避开 activity pill，宠物隐藏或 bridge 不可用时回退菜单栏；从 Codex 宠物开始的拖拽被两个 admission 忽略。

**值得肯定的三点**：① 定位上是收紧而非扩张——"never both"、"Codex mode never starts the native pet"，Delores 借外部锚点而不是养第二只宠物，Companion「被找到」的职责未变；② 技术上克制——只读不改 Codex renderer、有自然回退、仲裁有测试；③ 架构文档记录极详尽（方向、pill 避让、卡片几何、回退条件全覆盖）。

**两处定位层缺口（本次复评的核心新发现）**：

1. **宪法未认领「外部锚点」概念。** `delores-product.md` 的 Companion 章节仍是旧五职责/五禁，没有一句话说 Companion 可以是外部视觉锚点；行为全写在 delores-architecture.md（设计/架构层），README 更新了叙事，唯独定位层缺位。按宪法自己的裁决顺序，这属于「定位层概念变化」，应在 delores-product.md 落位——哪怕只有三行，像 snap 那次一样。
2. **单应用特化未拍板。** 377 行 probe + 硬编码端口 + "uniquely identified Codex overlay"，是 Codex 专属集成。产品决策悬而未决：这是要泛化为「任意带桌宠的 AI 工具的外部锚点」（external anchor 作为通用概念位），还是接受 Codex 为有意特例并记录理由？前者意味着 probe 需要抽象为协议，后者意味着下一个类似工具会再长 377 行。**不需要现在实现泛化，但需要现在记录取向**——否则这是第 4 个「代码先行、宪法后补」的实例。

### 2.3 「Selection Toolbar」命名（`07758dfb`）：踩在词汇表 Avoid 词上 ⚠️

设置里 Context Surface pane 改名 "Selection Toolbar"。三个事实叠在一起：

- `CONTEXT.md` 领域词汇明确写着 Context Surface 的 **_Avoid_ 就是「划词工具栏（selection toolbar）、快捷菜单」**；
- 宪法 Product boundaries 写着 Delores is not "the old selection toolbar embedded unchanged inside Tinycast"；
- 词汇表与宪法都未更新以承认这个用户文案层命名。

人家必须说句公道话：**从用户视角这个改名方向可能是对的**——"Context Surface" 是产品内部术语，泄漏到设置文案反而难懂。真正的问题是「两层命名」没有治理规则：内部领域词汇（Surface）与用户文案（Selection Toolbar）的关系没有在任何文档声明。而且三个 Surface pane 的用户命名风格**不一致**：Selection Toolbar（用户文案化）/ Companion Surface（保留内部术语）/ Search Box（用户文案化）——一半一半。下一个读 CONTEXT.md 的 agent 会认为 "Selection Toolbar" 是违规命名又改回去，形成震荡。

> 建议：在 CONTEXT.md 为 Context Surface 词条补一条两层命名注记（内部语言 Context Surface / 用户文案 Selection Toolbar 及理由），并统一三 pane 的用户文案风格；或改用一个不在 Avoid 词表里的直白词。

### 2.4 Action × Surface 矩阵：代码已拍板、文档未认领 ⚠️

`DeloresActionSurfaceMatrix` 用五档可见性（primary / available / resultCard / handoff / hidden）精确回答了上次评审的「矩阵拍板」建议，且 `resultCard` 档把「结果卡升级可见但不算目录行」这一微妙区分编码成了类型——设计质量很高。**但它是作为代码事实存在的**：docs 全目录零记录，action-core 文档里四个「未决产品问题」原样悬着，与代码现状已经脱节。矩阵 + `.ask` 的 resultCard 位实际上已经替「Ask AI 上不上 bar」这个未决问题给出了答案的骨架。

> 建议：矩阵表写入 `delores-product.md`（或 action-core）作为宪法附表，同步关闭对应未决项；这只需文档工作，不需要动代码。

## 4. 结论

**漂移主轴已经从「形态落位错误」收敛为「文档与宪法滞后于代码」。** 这是最健康的一种滞后——代码走在正确方向上（矩阵、外部锚点、边界脚本都是加强而非侵蚀定位），且修复响应速度证明了评审-修复闭环在运转。当前最要紧的不是写新代码，而是**让宪法追上代码**：三份文档补写（Codex 定位条目、矩阵入宪、两层命名注记）全部是纯文档工作，加起来预计不超过一页，却能消除全部三处新漂移。

> 元观察：`check-product-boundaries.sh` 已经把「README 三形态」「退役文档归档」变成了断言。下一步可以把「宪法包含矩阵表」「CONTEXT.md 与 Settings 命名一致」也纳入该脚本——让漂移检测本身自动化，是这个仓库治理的自然延伸。
