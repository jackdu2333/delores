# Delores 产品形态与设计评审

> 评审日期：2026-09-22 · 评审视角：产品形态（定位、Surface/Capability 边界、产品叙事）与设计（交互、视觉系统、可达性）
> 证据基线：`docs/` 五份产品/设计文档 + `Tinycast/` 代码现状盘点 + `Packs/LegacyFeatures/` 退役清单 + `Tests/` harness 覆盖面

## 0. 总评

**这是一个「宪法先行」纪律罕见严格的产品：产品形态骨架（3 Surfaces / 1 Core / N Capabilities）成立，且在代码里基本兑现。主要问题不在形态设计本身，而在三处「叙事与落位的漂移」——设置信息架构把 Core 能力寄居在 Surface 名下、两份退役能力文档仍按在售描述、双 Action 目录未合一使「一次配置全跟随」的宪法承诺打折。设计层工艺（token 体系、带实测依据的设计规则）是同类项目少见的水准；但跨 Surface 材质四重奏、浅色主题对比度欠账、Companion 可达性缺口是三笔要还的设计债。**

逐层裁决：

| 层 | 裁决 | 一句话 |
| --- | --- | --- |
| 发心（why） | ✅ 通过 | 轻量意图层、最小充分形态；9 问决策测试可执行、可否决 |
| 定位（what） | ⚠️ 漂移 | 三形态/一核心骨架成立，但设置 IA、双 Action 目录、升级入口三处漂移 |
| 设计（how） | ⚠️ 有债 | token 与交互工艺一流；欠材质四重奏、浅色 1.2:1、Companion a11y 三笔债 |
| 架构（boundaries） | ✅ 通过 | seam 账本齐整、harness 强制 Model 纯层；snap/divider 正确降级为 capability |
| 实现（code） | ✅ 通过 | Swift 6 严格并发；但 UI 层无自动化验证（本评不展开） |

## 1. 产品形态评审

### 1.1 发心与定位：站得住（✅）

- **三层决策宪法是本产品最强的资产之一。**「发心→定位→设计→架构→实现」的决策顺序、"实现便利不能反过来修改产品发心" 的硬约束、加上 9 问产品决策测试，构成了一套可执行、可否决的产品治理机制。北极星表述（"less like launching software and more like macOS gaining a useful layer of intent"）精准且能指导取舍。
- **形态/能力区分（Capabilities are not forms）是这份产品设计最锋利的一刀。** Window Snap / Split Divider 明确降级为 capability（"transient affordance attached to a gesture the reader was making anyway"），Notes 明确 "capability, not a fourth surface"——文档与代码在此一致，`Packs/LegacyFeatures/` 退役清单也守住了 "retired capabilities stay outside the active target"。
- **Companion 的五条 "must not become"**（不是聊天客户端/Action 目录/模型配置面/历史系统/独立 AI runtime）是全产品最好的边界写作，直接可当验收清单。代码兑现度也高：wander 注入随机 + 固定种子回放测试、shell 几何以 `bodyRadius` 为参数、尺寸只允许 48/96 两档（像素对齐防闪烁，理由写明）。

### 1.2 三处形态漂移（⚠️ 本评核心发现）

**漂移 A（最实质）：设置信息架构把 Core 能力寄居在 Surface 名下。**

现状：AI（`AISettingsView`）、QuickActions、MCP（`MCPSettingsSection`）、AIChat 的设置全部内嵌在 `Settings › Context Surface` pane 里（`AISettingsView.swift:574` 内再嵌 MCP）。但 AI / MCP / Action 是 **Core 能力**，Command Surface 的聊天、未来的 Companion 都消费它们。宪法说"用户配置一次 Action，期望这个选择跟随 Action 走遍 Delores"——现在想给 Command 聊天换模型的用户，会先走进一个叫 "Context Surface" 的设置页。

**这不是功能错，而是「能力属于 Core」这一产品命题在信息架构上没有兑现。** 形态层面的代价：Surface 与 Capability 的边界在用户可感知的地方（设置）被抹掉了，恰好抹在宪法最强调的那条线上。

> 建议（P0）：设置顶层引入 Core 能力区（如 "AI & Actions"），Context Surface pane 只留手势、条行为、入口开关。
> 验收标准：**为 Command 聊天换模型的路径不经过任何以 Surface 命名的 pane。**

**漂移 B：两个 Action 目录未合一，"One Action, multiple entry points" 只兑现了一半。**

`delores-action-core.md` 已如实记录：Context catalog（`DeloresContextAction` 四行）与 Quick Actions catalog（`BuiltInQuickAction` + custom）"overlap without agreeing"。Phase B 四步收敛**已完成**（共享 `DeloresActionDefinition` / `DeloresActionSession` / translate 双后端路由 / `outputCap` 统一），model route 与 prompt override 已按 id 打通——这是很大的成绩。但 catalog membership 仍分裂：`explain`/`search` 只在顶部条，`fixGrammar`/`rewrite` 只在 Command 面板。"同一 Action 配置一次、走遍全产品" 目前只在两条接缝上成立。四个未决产品问题（explain/search 上不上 Command、翻译是否继续受 AI 开关管辖、fixGrammar/rewrite 回不回顶部条、Ask AI row 去留）已明文列出，但尚未拍板。

> 建议（P1）：拍板一张 **Action × Surface 可见性矩阵**，作为宪法附表写入 `delores-product.md`，同步关闭 Phase C 的悬置问题。

**漂移 C：升级路径（Context → Command）是产品故事的主干，却没有入口。**

宪法 "Surface escalation" 把 Context → Command 列为正式路径；`delores-architecture.md` 的 handoff 基建全部就绪且有测试（`AIChatCoordinator.ask`、`isChatOnScreen` 合并语义、handoff 动画、pinned 状态保留）——但 **没有任何 shipped row 是 `.ask`**（"问 AI" 作为 "解释" 的重复品被退休）。结果是：任务要长大时，用户只能自己按 ⌥Space 重新开始，上下文衔接靠手动重选。基建备而不用是健康的，但产品故事缺个句号：要么补一个 Ask AI / 继续追问 row，要么在宪法里把该路径明确改写为"预留"。

> 建议（P1）：与漂移 B 的矩阵一起拍板；若不 ship，宪法措辞从"路径"降为"预留 seam"。

### 1.3 产品叙事的对外口径（⚠️ 漂移 D，轻）

- **README 把 Spatial Window Snap 与三 Surface 并列为"核心交互形态"1/2/3/4**——宪法明确 snap 是 capability 不是形态。对外叙事应与宪法同口径，否则新读者会形成"四形态"印象。
- **两份退役能力文档仍在按在售描述**：`docs/features/window-management.md`（"35 commands… Settings › Window & Split Screen is the switch"）与 `docs/features/window-layouts.md`（布局编辑器）。实际：`CommandID.swift` 仅 24 个命令且无任何 window 命令、设置只剩 Split Screen pane、布局编辑器已随退休包进 `Packs/LegacyFeatures/`。**这是文档层最严重的漂移**——照文档操作的用户或 Agent 会找不到所描述的产品。`docs/architecture.md` 的 `WindowLayoutStore`、"About 独立窗" 两处描述也过时。
- 反向缺口：Companion sprite 体系只有 sprite 文档覆盖，Onboarding / TextInjection 无 feature 文档（轻微）。

> 建议（P0，纯文档）：window-management / window-layouts 加 "Archived（moved to Packs/LegacyFeatures）" 头或移入 `Packs/LegacyFeatures/docs/`；README 形态口径统一为三形态；architecture.md 两处过时描述修正。这符合项目自己在 `delores-backlog.md` 建立的快照纪律。

### 1.4 「轻量」的产品属性：交互层成立，配置层偏重（⚖️）

- 发心的"轻量" = 只露出任务必需的界面。**交互层兑现得很好**：nothing → small surface → done → nothing；禁用能力不装监听/轮询；surface 干净退场。
- **配置面偏重**：20 个 Settings pane、Command Surface 内 10 个 screen（launcher/uninstall/quicklinks/fileSearch/menuSearch/switchWindows/clipboard/ai/aiHistory/calculatorHistory）、约 15 种面板/窗口。宪法允许能力生长（"Capability can grow"），Command 也确实是"任务可以长大的地方"，继承 Tinycast 成熟底盘有其合理性。真正要守住的是**不给 Companion 和 Context 加第四份配置、第四个入口**（五禁已写死，目前守住了）。
- Notes 是唯一自带 titled window 的能力，文档明确 "capability, not a fourth surface" 并把 chrome 单独记录——口径守住了。

### 1.5 手势治理：宪法条文变成可测代码（✅✅）

"one physical gesture belongs to exactly one consumer" 落到 `DeloresSurfaceInteractionGate` + 350ms 释放覆盖 + 单持有者规则 + `Tests/delores-context-test.swift` 断言；Huaci 的 "Ghost XOR Companion" 互斥旧逻辑被正确替换为"开关可同开、手势不可同消费"。**这是本项目方法论的最佳样本：宪法条文 → 单一仲裁者 → harness 断言。** 建议把这个模式写进 delores-product.md 的实施范例。

## 2. 设计评审

### 2.1 视觉系统：一流的规范纪律（✅✅）

`docs/ui.md` 本身就是本项目最大的设计资产，水准体现在三处：

1. **单一 token 源 + 冻结基线**：`Theme.swift` 唯一写数的地方；Dark 分支字面冻结（是 forced-dark 时代的实测值）、Light 可调；`InterfaceMetrics` 只存 scale、派生 token 组合已缩放部件（"an AppKit frame can never disagree with the SwiftUI view inside it by a point"）。
2. **每条规则都带实测依据**：497pt vs 428pt 的 `NSHostingView` 尺寸吞噬教训、IconStyle 通知 25–120ms 延迟与 160× 重绘成本、`Form` 400 行 750ms 实测、hover 的两个 SwiftUI 反直觉行为（"event type is not evidence the pointer moved"）……设计规则以 measured fact 为据而非口味，这在设计规范里非常罕见。
3. **语义正交的 Dialog 体系**：icon（是什么）/ tone（多严重）/ button role（点了会怎样）三轴独立互不推导，"collapsing any two of them back together is a regression"——把语义学写进了设计规范。配套的 HUD/Dialog 分工（dialog 问、HUD 报）、玻璃只给浮控件（"content takes the panel recipe"）都自洽。

配套的交互设计同样成熟：三段式结果卡（Ready → Working → Result）解决 streaming 抖动；**Pin 的语义选对了持久对象**（持久的是选区不是面板）；Retry/Follow-up 不离开 island（"第二个动作从不用重新选一遍"）严格贴合发心"不重复提供上下文"；追问 10 轮 / 8000 字符成对裁剪的理由（"unpaired question teaches a model to answer something nobody asked"）写进了规范。

一处可发现性小风险（记录在案的 deliberate cost）：island 不抢键盘（`becomesKeyOnlyIfNeeded`），Escape 在点进 follow-up 字段前属于用户 App——规则对用户不可见，建议给 follow-up 字段加一个可发现的 focus 提示。

### 2.2 设计层三笔债（按危害排序）

**债 1：浅色主题玻璃基底对比度（实际缺陷，非口味问题）。**
`delores-backlog.md` item 4 已记录：全屏黑菜单栏下系统玻璃变黑、浅色主题文字对比度仅 **1.2:1**，参考实现的 `surfaceScrimOpacity`（浅 0.30 / 深 0.36）未采用；因波及 palette/HUD 上游组件一直搁置。WCAG 正文 4.5:1 是及格线。**建议列为 P1**：先做一次浅色桌面实测对比度审计，再决定是补主题纱还是调 `panelScrim` 浅色分支（后者本就在"可 retune"范围内，波及面小）。

**债 2：Companion 可达性缺口。**
Companion 无 `accessibilityLabel`、Delores 自有代码无菜单栏入口——**键盘-only 用户完全不可达桌宠功能**（backlog item 7 仍 open）。自绘面板越多（Dialog/HUD/PopoverMenu 全自绘），VoiceOver/Focus 覆盖越要逐个补；Notes switcher 的 VoiceOver actions（activation/Rename/Trash 带真实标题）是现成的好样板。**建议列为 P1**：a11y label + 菜单栏入口一起做，Dialog/HUD 的 VoiceOver 覆盖按 Notes 样板推广。

**债 3：跨 Surface 材质四重奏 vs "一个产品的感觉"。**
北极星承诺 "They should never feel like they used several products"，但现状材质语言有四种：Context = Liquid Glass、Command = scrim + blur（hudWindow）、Companion = 像素精灵无材质、Settings = 系统 stock Form。架构文档把前两者差异 "recorded rather than resolved"（辩护理由：同屏只有 handoff 淡出的瞬间）——这个辩护对**材质**成立；但"一个产品的感觉"不只靠材质，目前能跨四重奏共享的锚点是 motion（`Theme.Duration` / `MenuMotion`）、keycap/typography、圆角语言、L10n 语气。

两点具体建议（P2）：
- 做一次**跨 Surface 统一性锚点审计**（motion/typography/keycap/圆角/语气五项），产出一页 "Delores look" 规则并入 `ui.md` 或 `delores-product.md`。
- **把像素桌宠 vs Liquid Glass 的反差明确写成设计层的品牌决策**（治愈系情感锚点，刻意为之），而不是留在架构文档当"差异备忘"——否则下一个 restyle 会把它当成未解决问题"统一掉"，那才是真正的损失。

补充（P2）：UI 层无自动化验证（island/Companion/snap/divider 不在 harness 编译清单），设计规则大多是像素级裁量（concentric corners、edge dissolve 带宽），restyle 风险全靠文档约束。island 已有 `CGWindowListCopyWindowInfo` 外部测量的先例，建议把该做法脚本化并扩展到 snap island / divider 的关键几何。

### 2.3 文案与本地化（小项，收尾即可）

- `Localizable.xcstrings` 552 keys、英文源 + zh-Hans，Settings / 菜单栏干净；漏网：palette 8 处 `.help(...)` 字面量、`RootPaletteView` 的 `Text("AI Chat")`/`Text("Actions")`（走 catalog 但不经 L10n 入口）、`AppCore.swift:330` 一处提示串。约 98% 合规。
- 建议：翻译记忆里挂一份 `CONTEXT.md` 领域词汇表（Surface/Capability 保留英文、禁用"划词工具栏"等 Avoid 词），保持三形态命名在两种语言里不漂。
